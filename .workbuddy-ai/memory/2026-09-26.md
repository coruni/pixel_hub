## 昵称渲染收敛为组件（Nickname / NicknameText）

- 用户建议「封装一个昵称组件」。动机是当时 `nameColorClass` / `nameColorBrightClass` 散在 8 处调用点，每处都要自己 `await getIncentive()` 再手选色阶——**选错不报错，只会静默变成对比度不足**。
- 拆成两个文件，因为「配置只在服务端能读，但评论区/悬浮卡是客户端组件」：
  - `src/components/ui/NicknameText.tsx` —— **纯渲染**，不带 `"use client"`、不引任何 server 依赖，因此服务端与客户端都能用（被客户端组件引用时随之一并进客户端包）。负责：按 `tone` 选色阶、`fallbackClassName` 兜底、`name ?? username` 回退。颜色类固定排最后，调用方误在 `className` 写颜色也盖不掉特效色。
  - `src/components/ui/Nickname.tsx` —— **async 服务端组件**，读 `getIncentive().decoration.nicknameEnabled` 后转交 NicknameText；props 类型是 `Omit<NicknameTextProps, "enabled">`。客户端组件引它会直接编译失败，正好当护栏。
- 组件对外暴露的是 `tone`（`light` / `dark`）而不是「用哪支函数」——「这处底是深是浅」只有渲染点知道，让调用方去猜函数名正是之前出错的地方。

## 主页背景遮罩改为后台可配（incentive.decoration.bgMask）

- 需求：把 `.profile-bg-pc` 里硬编码的 mask-image 提成后台可填字段，**原值即默认值**。
- 默认值（就是此前写死在 CSS 里的那条）：
  `linear-gradient(to right, rgba(0, 0, 0, 1) 0%, rgba(0, 0, 0, 1) 6%, rgba(0, 0, 0, 0.55) 14%, rgba(0, 0, 0, 0) 24%, rgba(0, 0, 0, 0) 76%, rgba(0, 0, 0, 0.55) 86%, rgba(0, 0, 0, 1) 94%, rgba(0, 0, 0, 1) 100%)`
- 落点：`points-config.ts` 的 `PROFILE_BG_MASK_DEFAULT` / `PROFILE_BG_MASK_MAX`(600) / `safeBgMask()`，字段挂在 `incentive.decoration.bgMask`（后台「装饰」区块）。
- **传递手法：CSS 变量 + 内联覆盖**。`globals.css` 的 `.profile-bg-pc` 改成声明 `--profile-bg-mask` 默认值 + `-webkit-mask-image: var(--profile-bg-mask)`；渲染点在同一个元素上写内联同名变量。内联自定义属性优先级高于样式表声明，所以选择器不用动、也没有第二份渐变需要同步。**改默认值要同时改 globals.css 与 PROFILE_BG_MASK_DEFAULT 两处**（各自注释里都写了）。
- 三个渲染点：`u/[username]`、`resources/[slug]`（**共用同一个值** —— 同一张图铺两处，形状不一致等于作者预览骗人）、设置页 `ProfileBgForm` 的预览（服务端算好传 `bgMask` prop，客户端不再复刻渐变）。`as CSSProperties` 的写法沿用 `SidebarLayout` 的 `--rail` 先例。
- **不在 zod 里 refine 的原因**：配置是整份替换，一个字段不合格会让 `safeParse` 整体失败、把管理员其他设置一起回落默认。所以只让坏值失效：`safeBgMask()` 在渲染前过形状校验，不合格退回内置遮罩，影响止步于背景。白名单只放行渐变写法（`linear|radial|conic-gradient`，可 `repeating-`，字符集 `a-zA-Z0-9\s.,%()#_-`），挡掉 `url()`（能发外部请求）与 `var()`（注入面）。
- **不需要数据库迁移**：bgMask 存在 `SiteSetting` 的 JSON 里，存量数据缺这个键由 zod `.default()` 补（`withGroupDefaults` 已覆盖分组缺失的情况）。
