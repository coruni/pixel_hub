# 2026-09-21

## 大文件上传优化：OneDrive Graph 分片与重试调优

范围经用户确认，只做「分片与重试调优」——不动接口契约、不加断点续传持久化、不改流式通道（`/attachment/stream` 仍是单请求 PUT）。

### 改动文件（3 个）

- `src/lib/upload-config.ts`：新增 Graph 分片常量与收敛函数
  - `GRAPH_CHUNK_MULTIPLE = 320 * 1024`（Graph 硬约束：每个 byte range 必须是 320 KiB 整数倍）
  - `GRAPH_CHUNK_MIN = 5 * MIB` / `GRAPH_CHUNK_MAX = 40 * MIB`（Graph 要求单请求 < 60 MiB）
  - `GRAPH_CHUNK_BYTES = 40 * MIB`（默认值，= 128 × 320 KiB）
  - `snapChunkBytes()`：把任意输入收敛到 [min,max] 内的 320 KiB 整数倍，兜住服务端下发的旧值/误配值
- `src/app/api/upload/attachment/session/route.ts`：`chunkSize` 由硬编码 `10 * MIB` 改为共享常量 `GRAPH_CHUNK_BYTES`（导入从 `MIB` 换成 `GRAPH_CHUNK_BYTES`）
- `src/lib/upload-attachment-client.ts`：主要工作量
  - 新增 XHR PUT 原语 `putBlob()`，替代原先的 fetch 分片上传；统一「进度 + 超时 + 取消」
  - 分片循环改为**偏移驱动**：`uploadViaChunk` 按服务端权威偏移推进，不再是无脑 `start += chunkSize`
  - 重试前先 `GET uploadUrl` 取 `nextExpectedRanges` 对齐（Graph 允许对 uploadUrl 直接 GET）
  - 处理 202 / 200 / 201 / 416 / 429 / 5xx 全部分支；416 = 服务端已有该段，可重试
  - 尊重 `Retry-After`，取不到才退回指数退避（上限 60s）
  - 双层超时：60s 无进展（`STALL_TIMEOUT_MS`，仅在有进度事件后启用）+ 30min 绝对兜底
  - `uploadAttachment` 新增第 4 个可选参数 `opts?: { signal?: AbortSignal }`，导出 `UploadCancelledError`
  - 进度改为字节级且单调递增，传输中封顶 99，100 只在服务端确认后发出

### 关键决策与坑

- **为什么用 XHR 而不是 fetch**：fetch 读不到上传字节进度（ReadableStream 请求体拿不到已发送字节数），大文件没进度条等于界面卡死。XHR 自带 `upload.onprogress` / `timeout` / `abort`。
- **stall 超时只在收到过进度事件后才启用**：一次进度事件都没有时无法区分「慢」和「死」，误判会让正常但缓慢的上传反复重传。这种情况交给 `xhr.timeout` 兜底。
- **先 settle 再 abort**：`xhr.abort()` 触发的 `onabort` 是排队事件，必须先 `finish()` 落定，否则抛出去的是 onabort 的兜底文案而不是「无进展」。
- **非末片收到 200/201 不能当已传完**：少数网关会把 202 折叠成 200，若在中间片收到就按「本片已收下」继续推进。
- **偏移推进语义**：`sendRange` 只会返回两个来源的偏移（202 的 nextExpectedRanges 必然 > offset；重试对齐后的服务端状态必然 ≠ offset），两者都可直接采信，包括服务端要求回退的情况。回退由 `maxRanges = ceil(size/chunkSize)*4 + 16` 兜住防死循环。
- **40 MiB 的取舍**：往返次数大幅下降（2GiB 从 205 片降到 52 片，10GiB 从 1024 降到 256），但单片失败重传的字节也变多。Graph 官方在稳定高速链路下推荐 10 MiB。若站点用户多在弱网，把 `GRAPH_CHUNK_BYTES` 调回 `10 * MIB` 即可，客户端原样跟随服务端下发值。

### 未覆盖 / 后续

- **未做端到端真实上传验证**：需要已登录会话 + 数据库 + 已配置的 OneDrive 云盘，本轮只做到类型/静态/构建层面。重试对齐、stall 超时、取消这些分支没有真实网络故障注入过。
- **取消能力已具备但未接 UI**：`uploadAttachment` 现在接受 `AbortSignal`，但 `UploadWizard` / `av-section` / `version` 三个调用点都还没传，也没有取消按钮。要做 UI 需要单独走视觉验收（AGENTS.md 要求 7 档宽度 + 明暗主题截图）。
- **断点续传（刷新后从已传字节继续）未做**：需要客户端持久化 uploadUrl（localStorage）+ 服务端暴露会话状态查询，会话过期/换盘/换用户边界要单独设计。
- **流式通道仍是单请求 PUT**：无云盘的自托管部署传 GB 级文件仍会被反代 `client_max_body_size` / 超时掐断，且中断即全部作废。

## 补做：自建验证台，闭合上一轮的证据缺口

上一轮结束时把「没有端到端真实上传验证」列为最大缺口。本轮发现项目的验证通道本身是坏的，于是自建了一个。

### 发现：项目的测试脚本全是死链

- `package.json` 里的 `test:smoke` / `test:admin-data` / `format` 都指向 `_test/` 目录，但**该目录在磁盘上不存在、也未被 git 跟踪**，且不在 `.gitignore` 里。
- 实际执行 `npm run test:smoke` → `Cannot find module 'E:\project\pixel_hub\_test\smoke.mjs'`。
- 结论：这是 checkout 的基线缺陷，AGENTS.md 要求的 `npm run test:smoke` 在此仓库**无法执行**。不是本次改动造成的。

### 自建验证台：`_tmp_upload_verify.mts`（项目根，被 `.gitignore` 的 `_tmp_*` 覆盖）

用 Node 驱动**真实的** `src/lib/upload-attachment-client.ts`，不复制业务逻辑：

- 本地 `node:http` 服务模拟 Graph upload session 语义（202/201/416/429/500、`nextExpectedRanges`、GET 查询会话状态）
- 一层 `XMLHttpRequest` shim（模块用 XHR 才能拿上传进度）：`upload.onprogress` 按 512 KiB 分片触发、`timeout`、`abort`（abort 事件用 `queueMicrotask` 异步派发，与真实 XHR 一致）
- 包装 `globalThis.fetch` 把相对路径补成 `http://127.0.0.1:PORT`，并按用例注入 `?script=&chunk=&nocloud=` 控制剧本
- 通过故障剧本数组 `["ok","fail500","commit-then-500","partial","stall","slow"]` 按第 n 次 PUT 注入

### 关键工程坑（下次直接复用）

- **脚本必须用 `.mts` 后缀**：项目 `package.json` 无 `"type": "module"`，`tsx` 会把 `.ts` 当 CJS 处理，顶层 await 直接报 `Top-level await is currently not supported with the "cjs" output format`。
- **`tsconfig.json` 的 `include` 含 `**/*.mts`**：放在项目根的验证脚本会被 `npx tsc --noEmit` 一起检查。要么让它类型干净，要么它会把 tsc 弄红。
- **函数声明式闭包拿不到类型收窄**：`const s = map.get(k); if (!s) return;` 之后再声明 `function f() { s.x }`，TS 仍报 `'s' is possibly 'undefined'`（函数声明会提升）。解法是取一个非可选别名 `const s: Session = found;`。
- 用例断言本身也会写错，且错的断言比没断言更危险。本轮自查改掉三处：`7864320` 恰好是 320 KiB 整数倍（不能用「非整数倍」判断中途续传）、重试场景下 `putCount === ranges.length`（两者同步增长，不能用来判断「发生了重试」）、取消用例靠时间竞态不可靠（改为让服务端慢响应 3s，abort 才确定落在请求飞行中）。
- mock 里 `/complete` 硬编码 `size: 0` 导致 6 个用例假失败——**测试桩的 bug 会被误读成被测代码的 bug**，先怀疑桩。

### 验证结果：11 个场景 / 35 项断言 ALL PASS

| # | 场景 | 关键结论 |
|---|---|---|
| 1 | 顺利路径 | 12MiB/5MiB=3 片，起点与长度均落 320 KiB 整数倍，字节逐字节一致 |
| 2 | 服务端下发 41943041（非整数倍） | 被收敛到 40MiB，线上起点 0/41943040/83886080 全合规 |
| 3 | 500 后重试 | 服务端确实没收到 → 原区间重发（PUT 两次），完整性未破坏 |
| 4 | **已落库却回 500** | 靠 GET 对齐跳过，该片只 PUT 一次，**总 PUT 数 = 分片数，零多余重传** |
| 5 | 429 + Retry-After: 1 | 实际退避 1052ms，未出现多余重传 |
| 6 | 部分接收（只收半片） | 从 7864320 精确续传，半片续传未错位 |

### 本轮顺带修掉的两处

- `UploadCancelledError` / `TransferInterruptedError` 补 `name`（此前日志里只会显示 "Error"，分不清取消还是真失败）
- `NO_CLOUD` 回退分支补 `onProgress?.(100)`（此前该通道进度条永远停在 0，与文档承诺的「完成时收到一次 100」不符），并修正 `wizard-sections.tsx` 里因本轮改动而过时的进度语义注释
