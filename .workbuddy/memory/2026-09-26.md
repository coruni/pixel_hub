## 第三批：结构性优化（2026-09-26 晚）

三件事：评论树加 rootId、Feed 改 keyset 游标、PV/限流/下载链路减少数据库往返。

### ① 评论树 rootId（`prisma/migrations/0016_comment_root_id.sql` + `src/lib/comments-paging.ts`）

- `Comment.rootId`（可空）指向**拓扑根**，根自己指向自己。目的：把「某根的全部后代」从逐层 BFS
  （每层 1 次往返、靠 `MAX_REPLY_DEPTH=20` 兜底成环）变成一条 `WHERE rootId = ?` 等值查询。
- **口径关键**：`rootId` 记录拓扑根、**不随删除变化**，而评论区可见口径是「父被删则回复上移自成根」。
  所以取回复时必须加 `NOT: { parent: { status: { not: PUBLIC } } }` —— 上溯链上任一级父非公开，
  它的直接子行就命中该条件被排除，整支后代自动不进结果集。少写这一条会把「自成根」的行重复挂到原树上。
- `fetchRepliesByRoot` 保留 BFS 作为**回退分支**（`fetchRepliesByRootBfs`）：迁移未执行时 rootId 全为 null，
  等值查询取不到行 → 自动回退。代码可以先于迁移上线。迁移跑完可整体删掉 `fetchRepliesByRootBfs` /
  `MAX_REPLY_DEPTH` / `FrontierItem`。
- 迁移回填顺序：① 根（`parentId IS NULL` **或** `父 status <> PUBLIC`）→ 自己；② 递归 CTE 从根逐层下推
  （必须自顶向下，子才能继承父），带 `depth < 64` 防脏数据成环。幂等 + 非破坏，只有 ADD COLUMN /
  CREATE INDEX / UPDATE。
- 写路径 `addCommentAction`：回复继承父的 `rootId`（取不到就留空、交给回退分支）；根楼层在**同一事务内**
  再补一次 `update rootId = 自身 id`（create 拿到 id 才知道）。

### ② Feed 改 keyset 游标（`src/lib/feed-paging.ts` / `queries.ts` / `feedmore.ts` / FeedInfinite.tsx）

- 新增 `FeedCursor { k, t, id }`（主排序键值 / publishedAt 毫秒戳或 null / id 决胜键）+ `parseFeedCursor`。
- `getFeed` 加 `cursor?: FeedCursor`，返回 `nextCursor`。有 cursor 时**不带 skip**，改把游标展开成
  keyset 条件的 `where.AND`。`skip = (page-1)*pageSize` 在追页期间只要有新内容插入就会窗口位移，
  表现为重复或漏卡；游标锚定数据本身，与前面有几条无关。
- keyset 条件展开成字典序比较，**用 `lt` 而非 `lte`**（三键降序已唯一确定一行，lte 会把游标那行再取回来）。
- **`createdAt` 刻意不进 keyset**：它是 latest 排序在 publishedAt 之后的第三键，而 `id` 是主键，
  `(publishedAt, id)` 已唯一；带上只会让 OR 分支翻倍、SQL 更贵（除非哪天冒出一个能与现有 id 并列的行，
  否则换不到任何正确性）。
- **`publishedAt` 可空是最大的坑**：Postgres 的 `DESC` 默认 NULLS FIRST，而 `lt` 对 NULL 恒为 UNKNOWN。
  游标必须显式区分「还在时间区」/「已进 null 区」（`t === null` 时只排 `publishedAt: null`），
  否则 null 段的行会被整段跳过。popular/downloads 排序同理，`t === null` 分支不能写成 `lt`。
- 全文检索（`relevanceOrder`）分支**不接游标**（相关度顺序不是列值），`nextCursor` 返回 null。
- 客户端：`pageRef` 换成 `cursorRef`；**删掉了「整页都重复 → 终局」这条补丁** —— 那是 offset 漂移的
  workaround，游标分页下正常不会发生，真发生也只该跳过、不该终止流。按 id 去重保留作兜底。
- 实测：真实库上 keyset 逐页取 25 条与 offset 前 25 条**完全一致**（`_test` 临时脚本，已删）。

### ③ PV / 限流 / 下载链路减少往返

- **限流** `src/lib/rate-limit.ts`：原 `DELETE → COUNT → INSERT` 是 3 次 RTT，单条 CTE 合成 1 次。
  **坑**：Postgres 的 CTE 内各子语句看**同一快照**，所以 `counted` 数的是「清理前」的行数，
  谓词必须自己再写一遍 `ts >= cutoff`；只数全表会把过期行算进配额，限流被历史流量撑大而失效。
  实测新旧实现逐次结果完全一致 + 过期行确实被清。
- **PV** `src/app/api/track/route.ts`：`visit.create` / `viewCount` 自增 / 1% 机会式清理原本各自
  独立 await（3 RTT），合并进一个 `$transaction`。ensure 语义不变（visit 失败则整批不成立）。
- **下载** `src/lib/download-record.ts`：两个 `count` 合成一条 `SELECT (子查询, 子查询)`；

  `incrementDownloadAction` 不再补发 update（原先那是两次独立往返，还可能只成一半）。
  ⚠️ `RecordDownloadResult.firstTime` 的语义随之变化：true 时计数**已经加过**，调用方不要再加。
  条件自增仍只对 `status = PUBLISHED`（与旧调用方口径一致）。

## 修 settle:auto 调度异常：unstable_cache 在无请求上下文时抛 Invariant（2026-09-26 23:0x）

**报错**：`Invariant: incrementalCache missing in unstable_cache ...`，
`at maybeAutoSettle → getIncentive → src/lib/incentive.ts:35`，每 15 分钟 tick 一次。

**根因**（读 `node_modules/next/dist/server/web/spec-extension/unstable-cache.js:60-70` 确认）：

请求 / 预渲染内有值。`src/instrumentation.ts` 的定时器是纯进程内代码，**永远没有**请求上下文，
所以走进 `getIncentive()` 必炸。**不是配置读坏了，是这套缓存在进程内根本不该被调。**

**修法**：新增 `src/lib/cached-in-request.ts`，导出 `cachedInRequest` / `cachedInRequestWithArgs`，
包装 unstable_cache 并**只对这条 invariant 文案**降级为直连数据库（其余错误照常抛）。
收口在一处，比在 9 个调用点各包 try/catch 稳。

**已迁移 9 处**（`grep -rn unstable_cache src/` 现在只剩包装文件自身）：
`site.ts` / `runtime-config.ts` / `upload-limits.ts` / `seo-config.ts` / `doc-config.ts`（带参，

**直接返回 promise**，而 `cache()` 要求回调是 async 函数 —— 改成 `async () => await readCachedIncentive()`。

**实测（无请求上下文的 tsx 进程）**：裸 `unstable_cache` 复现出同一条 invariant；包装后正常返回；

**根因（本次查清）**：Clash Verge 的 **TUN + fake-ip** 模式**全量劫持 DNS**。
`aws-0-ap-southeast-1.pooler.supabase.com` 解析成 `198.18.0.23`（Clash fake-ip 段
`198.18.0.0/15`）+ `2001:2::9`（fake IPv6）。**换成 8.8.8.8 / 1.1.1.1 查询也返回同一个 fake-ip**
（UDP/53 被 TUN 接管，无论问谁）。

**为什么 Python 探测"通"了而 Prisma 不通**：TUN 下 `connect()` 被 Clash 秒回（假成功），
但**服务端永远不发任何字节**。实测：连上后 `recv` 1.5s 超时（PG 正常会在客户端发 StartupMessage
前先静默，但这里连真握手都没有）。走 Clash HTTP 代理（`127.0.0.1:63602`）发 `CONNECT` 能拿到
`200 Connection Established`，但代理规则把这域名判给 **DIRECT**，直连又被 TUN 黑洞 → 依然无响应 5s。

**结论**：**不是代码/配置问题，是本机代理环境问题**。Prisma engine 不走 `HTTP_PROXY` 环境变量
（清了也没用，已验证），TUN 是网络层、绕不过。

**处置**：这类情况下**不要**反复重试探针、不要查 DNS、不要改 `.env`。要么在 Clash 里给
`*.supabase.com` 加 **fake-ip-filter / 走真实 DNS 解析**，要么临时关 TUN 用系统代理。
期间需要验证数据层逻辑时，改走**源码静态审查**（读函数体确认参数传递正确），
不要拿 DB 探测结果当阻塞项。

## 修 /browse 客户端包里混入 PrismaClient（2026-09-27 00:5x）

**症状**：`/browse?cat=music` 运行时抛
`Error: PrismaClient is unable to run in this browser environment, or has been bundled for the browser`。

**这是既有 bug，不是本次改动引入的**（用户纠正了我一开始「是缓存」的错误判断）。

**根因（精确定位）**：
```
FeedInfinite (client) / list-more (client)
  → ResourceGrid → ResourceCard / ResourceRow
  → ui/Nickname.tsx          ← 服务端 async 组件，越界
  → lib/incentive.ts (getIncentive)
  → lib/db/prisma.ts
```
`Nickname.tsx` 是**服务端 async 组件**（`await getIncentive()`），而 `ResourceCard` / `ResourceRow`
被客户端组件引用 → Next 把它们当客户端组件编译 → 把 `Nickname` 连同 `getIncentive` → Prisma
一起拖进浏览器包。

`Nickname.tsx` 的作者注释写着「客户端组件引不了本文件，正好当护栏」—— **这个护栏不成立**：
Next 不会因为「客户端组件引了服务端 async 组件」就编译失败，它只会把整条链打进客户端包，
然后在运行时炸。**别再依赖这类「编译器会拦」的假设**。

**为什么只有 /browse 报错**：`ResourceCard` 只在 **客户端路径** 下才被当客户端组件渲染 ——
`/browse`（`infinite` → `FeedInfinite`）和首页 `list-more`。`/tags/[slug]` 也用了 `FeedBrowser`
但没传 `infinite`，走服务端分支所以不炸。

**修法**（沿仓库既有的「开关走 prop」约定）：
- `ResourceCard` / `ResourceRow`：`Nickname` → **`NicknameText`**（客户端安全），
  新增可选 prop `nicknameEnabled = true`。
- `ResourceGrid`：透传 `nicknameEnabled`。
- `FeedInfinite` / `list-more`（client）：加 `nicknameEnabled` prop 并透传。
- `FeedBrowser` / `list.tsx`（server）：`getIncentive()` 取值传下去
  （走请求级 cache，与页面其它读取共享同一次查询）。
- 服务端调用点**不传即默认 true**，行为不变；客户端调用点必须传真实值。

**诊断方法（可复用）**：写一个 Node 脚本，遍历所有 `"use client"` 文件，
做依赖可达性遍历，**只统计值导入**（排除 `import type` / `import { type X }`，这些编译期擦除），
遇到 `"use server"` 停（RPC 边界）。命中 `db/prisma` 即输出完整路径。
- 第一版没排除类型导入，报出 4 个假阳性（`ResourceEditForm` 等走 `queries` 的其实都是 `import type`）；
  **必须区分类型导入与值导入**，否则结论不可信。
