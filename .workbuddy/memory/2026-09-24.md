## 排查：免审直发的内容是否参与贡献分
- 结论：**不参与**。`PUBLISH` 分全站唯一发放点 = `src/lib/actions/moderation.ts` 的 `approveResourceAction`（第 67–74 行，`after()` 里 `awardPoints`，actorId = 审核人）。
- 免审直发走的是 `src/lib/actions/resource.ts` 的 `directPublish`（第 184–185 行：`user.trusted || role === ADMIN/MODERATOR` → 直接 `status:"PUBLISHED"`），该路径**完全没有调 `awardPoints`**。

## 实施：免审直发补发 PUBLISH 分（`src/lib/actions/resource.ts`，+9 行）
- 加 `import { after } from "next/server"` + `import { awardPoints } from "@/lib/points"`；在 `createResourceAction` 的 `if (status === "PUBLISHED")` 分支首位（`queueIndexNowForResource` 之前、`redirect()` 之前）注册 `after(() => awardPoints({ ... }))`。
- `after()` + 紧随其后的 `redirect()` 的可靠性依据：**同一分支里 `queueIndexNowForResource` 本身就是 `after()` 实现**（`indexnow.ts:104`），现网已验证「redirect 前注册的 after 会执行」——不必再起浏览器复验。
- 验证：`tsc --noEmit` 零错误；`eslint src/lib/actions/resource.ts` 零告警；临时断言脚本 `prisma/_check-direct-publish.ts`（已删，备份在 `%TEMP%`）4/4 PASS —— 含反证「LIKE_RECEIVED 本人仍被拦」，确保不是函数恒返回 false 的假绿灯。
- **未处理的次生缺口**（保持最小 diff）：`restoreResource`（下架→恢复）与举报复核 `PENDING→PUBLISHED` 两条路径都不发 PUBLISH 分。对「审核通过」的资源无害（早已发过），但对**修复前直发的存量资源**，下架后恢复仍拿不到分。若要兜住，在这两处补同样的 `awardPoints` 是幂等安全的。
- **用户决定（08:33）：存量直发资源不追溯补分** —— 上面那处缺口就此关闭，不加回补逻辑、不跑额外脚本。只对新发布生效。
