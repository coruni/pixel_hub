### 核心洞察：断点互斥的层 + `:has()` 会串槽

两槽是靠 Tailwind 的 `hidden sm:block` / `sm:hidden` 互斥显示的，而 **`:has()` 只看「元素在不在
DOM 里」、不看它是不是 display:none**。原来那条不分断点的优先级规则

```css
body:has([data-profile-bg-owner]) [data-profile-bg-global] { display: none }
```

在新结构下会串槽：作者只设了**桌面端**那张图时，移动端的 owner 元素照样在 DOM 里（只是被
`sm:hidden` 藏着）→ 移动端访客自己的全局背景被无理由隐掉，而它本该照常显示。

改成按断点成对，并把属性名也带上槽位后缀（`data-profile-bg-owner-pc` / `-mobile`、
`data-profile-bg-global-pc` / `-mobile`）：

```css
@media (min-width: 40rem) { body:has([data-profile-bg-owner-pc]) [data-profile-bg-global-pc] { display: none } }
@media (width < 40rem)    { body:has([data-profile-bg-owner-mobile]) [data-profile-bg-global-mobile] { display: none } }
```

`width < 40rem` 与 Tailwind v4 的 `sm`（40rem）严格互补，不留空隙也不重叠。要点是让
「owner 存在」与「owner 此刻可见」在**同一个断点里**成立。

## 事故：发布资源失败 —— 事务内 catch 唯一键冲突把事务打成 aborted

用户贴线上容器日志。**表象**是 `prisma.media.updateMany()` 抛
`PrismaClientUnknownRequestError` + `code: 25P02 current transaction is aborted, commands ignored
until end of transaction block`，前面几行还夹着
`Invalid prisma.tagOnResource.create() invocation: Unique constraint failed on (resourceId,tagId)`。

**根因不在 media，在上一句的 tagOnResource.create。** Postgres 的交互式事务是「一旦有语句报错，
整个事务立刻 aborted」，之后每条语句都返回 25P02 —— **与 JS 层有没有 catch 无关**。
`tagOnResource.create().catch(() => null)`（注释写着「并发去重」）只吞掉了 JS 错误，事务在服务端
已经死了，于是紧接着的媒体认领必然炸，并把真正的根因盖掉。同文件里
`tx.tag.create().catch(() => tx.tag.findUnique(...))` 是同一个错误的另一处。

**为什么会有重复键**：`names` 只按名字去重，但两个不同输入名可以解析到**同一个 Tag 行** ——
命中链是 `findUnique(slug) ?? findUnique(name) ?? create`，用户同时填「云」和「yun」时
拼音 slug 都是 `yun`，第二条会经 slug 命中第一条刚建的标签 → 同一个 tagId 关联两次。
（`_resource-edit.ts` 里改名新建标签也有同款：`tx.tag.create` 撞 slug 唯一键 → catch → 全事务死。）

**修法**：新增 `src/lib/actions/_tags.ts`
- `findOrCreateTag(tx, name, slug)`：先按 name、再按 slug 双查（只查 name 会漏掉 slug 撞车），
  未命中用 `tag.createMany({ skipDuplicates: true })`（PG: `ON CONFLICT DO NOTHING`，
  冲突不报错、不中断事务）再回查。
- `linkTag(tx, resourceId, tagId)`：同样走 `createMany({ skipDuplicates: true })`，
  用返回的 `count > 0` 决定是否给 `Tag.count` 加一。
- 两个调用点（`resource.ts` 的 `createResourceAction`、`_resource-edit.ts` 的 `applyResourceEdit`）
  都改成「`linkedIds` Set 按 tagId 去重 + 上面两个 helper」，删掉全部 `.catch()` 兜底。

验证：`tsc --noEmit` 干净、`eslint` 3 个文件 0 error 0 warning。未做运行时实测。

**同一份日志里的另一条（与本 bug 无关）**：`failed to get redirect response TypeError: fetch failed`
→ `ERR_SSL_PACKET_LENGTH_TOO_LONG`。这是出站 HTTPS 被中间人/代理干扰（本机 Clash TUN 那类），
发生在 `autoSlugBase` 的翻译请求上；该函数有拼音兜底，不影响发布。

### 追认口径：名字不同但翻译出的 slug 相同 = 同一个标签，直接合并

用户：「新tag名字不一样 但是翻译的slug一样就直接合并。」

- **发布 / 改稿路径本来就符合**：`findOrCreateTag` 的命中链是「按 name 查 → 按 slug 查 → 才新建」，
  slug 撞上别人就复用那一行，既不报错也不新增词条（这正是上一节修掉重复关联键的底气）。
  优先级是 **name 优先、slug 兜底**：作者手填的名字若能对上，就按名字走；对不上再按 slug 归并，
  这样「同一概念、中英两种写法」不会各建一个词条。
- **管理后台的改名路径原本不符合**，已改：`renameTagAction` 原先在「slug 被别的标签占用」时
  **返回错误**（`自动生成的 slug「x」已被标签「y」占用`）。现在把校验唯一性那一步去掉，
  只留格式校验，然后统一判断合并目标：
  `name 变了且被占用` → 目标；否则 `nextSlug 与既存标签相同` → 目标。
  命中就调抽出来的 `mergeTagInto()`（转挂关联 + count 净增 + 删源标签 + audit），不命中才更新。
- `mergeTagInto()` 由原来内联在 `if (nameChanged)` 里的合并块抽出，且**关联建立改用
  `linkTag()`（createMany skipDuplicates）**，去掉那两段「先查 existing 再逐条 create」的写法 ——
  既是上一条事务铁律的要求，也让「转挂了几条」直接由返回的 count 说话。

`tsc --noEmit` 干净、`eslint` 2 个文件 0 error 0 warning。未做运行时实测。

## 修 bug：移动端背景始终套着 PC 的遮罩

用户：「移动端背景的遮罩还是使用的 PC 遮罩」。

**根因**：`safeBgMask(raw)` **不认识槽位** —— 它唯一知道「什么算默认」的方式是返回
`PROFILE_BG_MASK_DEFAULT`（桌面端那条左右两条带），所以 `profileBgMobileMask` 为 null 时
移动端拿到的就是 PC 遮罩。更阴的是它不会报错：这个值是通过**内联** `--profile-bg-mask` 传下去的，
内联声明优先级高于 `.profile-bg-mobile` 类自带的那份默认值 —— CSS 里写对的默认值被静默盖掉，
连源码都看不出破绽。

**修法**：
- `upload-config.ts`：新增 `PROFILE_BG_MASK_DEFAULTS: Record<ProfileBgSlot, string>` 作为
  槽位→默认值的**唯一事实来源**；把形状校验拆成私有 `maskShapeOk()`；
  `safeBgMask(raw, slot = "pc")` 按槽退回默认值；`isValidBgMask` 改用 `maskShapeOk`，
  **不再掺默认值** —— 填的恰好是另一端的形状也算合法（那是用户的正当选择，
  旧写法 `safeBgMask(v) === v` 在这种输入下会误判）。
- 四个调用点补 slot：个人主页、资源详情页、`GlobalProfileBgLoader`、设置页预览
  （`ProfileBgForm` 里读的是本槽的 `maskDraft`，槽位从 props 来）。
- 顺手消掉重复：`settings.ts` 的 `BG_MASK_DEFAULT` 与 `ProfileBgForm.tsx` 的 `SLOT_DEFAULT_MASK`
  两张本地映射都改成引用 `PROFILE_BG_MASK_DEFAULTS`（这类「默认值概念被抄成第二份」正是本次
  故障的土壤）。

`tsc --noEmit` 干净、`eslint` 6 个文件 0 error 0 warning。未做浏览器实测。
