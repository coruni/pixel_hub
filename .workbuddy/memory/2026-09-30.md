# 2026-09-30

## 图片上传去重：改用「压缩前源字节的 sha256」（修复「被压缩导致重复上传检测失效」）

**问题**：附件链路（`/api/upload/attachment` 三条通道）按「同一用户 + 同名 + 同大小」去重，
这套判定在**图片**链路上不成立 —— 图片落库前会被 sharp 重编码（≤1600/480 缩放、质量按后台配置、
格式可能换 webp，见 `media/process.ts`），`Media.size` 存的是**压缩产物**字节数，
与用户手上的原文件不是一回事；而图集 / 评论附图链路此前**完全没有去重**。

**改动**（新增 1 个模块 + 1 个迁移，改 5 个文件）：
- 新增 `src/lib/media/checksum.ts`：`sha256Hex(buf)`（源字节指纹）＋ `findReusableImage(uploaderId, checksum, scope)`
  （scope = `gallery` | `comment`；comment 额外要求 `commentId != null`，避免复用「原样落盘、没过缩图」的附件行）。
  命中后**复用旧存储对象、另建一条 Media 记录**（`resourceId`/`commentId` 是单值列，跨资源复用同一行会把图从上一个资源手里抢走）。
- `src/app/api/upload/route.ts`：算指纹 → 命中则跳过 `processImage`（sharp 三次编码 + 三次落盘）与
  三次存储写入，只补一条记录；响应多带 `deduped`；所有新行写 `checksum`。
- `src/lib/actions/social.ts`：`saveCommentImage` 加 `userId` 参数，命中即跳过压缩与落盘；
  返回类型抽成 `SavedCommentImage`（含 `checksum`），`createMany` 一并写 `checksum`。
- 连带修的两处「共享存储对象」隐患：
  - `src/lib/actions/admin-media.ts`：`purgeFiles(mediaId, keys)` 先反查**别的** Media 是否还在用这些 key，
    被别处引用的不删（否则清理一条孤儿记录会把另一个资源正在展示的图删成 404）。
  - `src/lib/storage/bucket-usage.ts`：按 `storageKey` 去重后再求和（同一物理对象只算一次，
    否则去重后一张图被重复计入桶用量、把桶提前顶到上限）。
- `prisma/schema.prisma`：Media 加 `@@index([uploaderId, checksum])`；
  新增 `prisma/migrations/0021_media_checksum.sql`（`ADD COLUMN IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS`）。

**实测（只读探针，已删）**：线上库 `Media.checksum` **列已存在**（历史 schema 就带，只是从没写过值），
索引只有 `Media_pkey / resourceId / commentId / uploaderId` —— 即**代码不依赖迁移即可上线**，
0021 只是补上 `Media_uploaderId_checksum_idx` 这个去重查询要用的索引。
