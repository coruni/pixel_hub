- 金额精度：一律整数「分」+ 万分比整数；分配用**最大余数法**（保证总额精确等于池子、结果确定性可复算）+ 单人封顶迭代（默认 40%，最多 3 轮收敛）。未发出余款结转下期，账目对平。

## 激励方案 v4：用户拍板 6 项决策（已全部落实）

用户原话决策：① PIX（不要中文名）；② 可设定但**创作者激励要匹配网站收入，不能一提现就倒贴**；③ 兑换比例可配、默认不变；④ 结算口径保持原样（点赞等默认不计入结算）；⑤ PIX 不可购买；⑥ **打赏也只能打赏代币**。

**② 的技术答案 = 偿付能力闸门（§3.4）**
- 不变式：`代币负债 L = Σ(balance+frozen) × 单价 ≤ 可用现金 C × (1 − buffer)`，buffer 默认 10%。
- `C = Σ收入(IN，已实际到账) − Σ已打款(OUT) − Σ其他支出(OUT)`。
- **两个强制校验点**：结算确认时（`L + 本次 ≤ C×(1−buffer)`，不足则拒绝并给出水位明细）、提现申请时（现金须覆盖所有未打款提现 + 本次）。
- 两道的原因：第一道保证"发出去的 PIX 有真钱对应"，第二道保证"兑现时钱还在"（防中间被挪走）。
- 前提纪律：**收入录入 = 钱已实际到账**，不是预计收入，否则水位公式是假的。录入界面要写死这句提示。
- 后台新增 `/admin/finance` 收支台账，驱动水位与前台筹资进度。

**⑥ 打赏改为站内 PIX 转账（§2.5）—— 架构级变化**
- 打赏**不再是收费点**（收费点从 3 个降为 **2 个**：站点赞助 + 容量扩容），不走支付通道、平台不经手真钱、无需审核打款。
- 计价用 PIX（预设 100/500/1000/2000 + 自定义），**前台不显示 ¥ 等值**。
- 只能用可用余额（冻结中的不能用）；不能打赏自己；不可撤回；**不产生贡献分、不计入结算**；公开打赏榜默认关闭。
- 结构上天然抗刷：**一笔打赏全站 Σ PIX 不变**（转出 = 转入），小号互打毫无收益。
- 数据模型：`TipRecord` + 两条 `CoinLedger`（`TIP_SENT` / `TIP_RECEIVED`）；`CoinReason` 增加这两个值。
- **PIX 总量只由激励池一次创造，打赏只是搬运** —— 所以「总量有限 + 真实资金背书」不会被破坏。
- 连带改动：`PaymentOrder` 删 `payeeId`/`payee`/`settledAt`，`OrderKind` 删 `DONATION`；支付订单**只有「收入进站」一个方向**，出款全在激励方案的提现口。

其他变更：代币统一叫 **PIX**（无中文别名）；`CoinAccount` 增 `lifetimeTippedOut`；后台新增 `/admin/withdrawals`（顶部常驻现金水位）；配置表增「偿付 buffer / 资金不足策略 / 打赏开关与范围 / 公开打赏榜」；验收增「偿付闸门」「打赏守恒（ΣPIX 不变、不产生贡献分）」两组反证；分期改四期（荣誉 → PIX 与结算 → 打赏与提现 → 可选）。

`payment-plan.md` 已同步：收费点 2 个、§2.2 改为「打赏已移出收费点」、`OrderKind` 删 DONATION、待拍板降为 3 项。

- 原方案里我按 cookie 去重（`dl_done`）已不可信 → 改为三级闸门：
  1. **主体级去重**：`DownloadCredit @@unique([resourceId, subjectKey])`，`subjectKey` = 登录 `u:<userId>` / 匿名 `ip:<ipHash>`。登录用户同时受作品×用户约束（换 IP 也再计不了）。

- `refId` 改为 `dl:${subjectKey}:${resourceId}`。
- IP 哈希复用 `track/route.ts` 惯例（`sha256(ip + AUTH_SECRET)` 取 16 位），**须抽公共 `hashIp()`**（`src/lib/ip.ts`），否则两处漂移导致跨表关联不上。已同步写入 `MEMORY.md`。

- 残留漏洞如实记录：换 IP 可绕闸门一（靠配额限损）；作者匿名下载自己作品识别不了。
- 新增风险项：**`x-forwarded-for` 可伪造** —— 若前面自建反代/CDN 是"追加"而非"覆盖"该头，闸门一可被绕过，上线前必须确认。

## 术语澄清：分成比例 ≠ 资金池（用户提问触发，已补进 §3.1）

用户问「分成比例就是资金池是吧？」—— 不是，且文档里**有两个名字极像的「池」**，这是真实歧义，已补 §3.1「两个池必须分清」+ §8 各归一处说明。

| 名字 | 是什么 | 归零？ | 前台位置 |
|---|---|---|---|
| **激励池 P** | 本期**应发额** `floor((R+上期结转) × 分成比例)`，是账目不是钱 | 每期重算，未发完结转下期 | `/creators` 各期公示 |
| **现金池 C** | 站上**真钱** = 累计收入 − 成本 − 已打款，跨期结存 | 不归零 | `/fund` 首屏水位 |

- **分成比例 = 那个「×」**，不是池子；乘出来的那块才叫激励池。
- 切出的 30% **一刻也没离开现金池**：收入全额进 C，30% 只让负债 `L` 上升；钱真正出去只在提现打款那一刻（§3.4 分离表）。
- **新增提示（重要会计选择）**：比例是对**毛收入 R** 切的，不是对利润（收入−成本）切的。所以成本占比偏高时 `L` 会比 `C` 长得快 → 顶破安全水位 → 结算确认被闸门拒。**长期被拒 = 比例相对成本结构定高了，该下调，不是 bug。定 30% 的隐含假设是「成本长期不超过收入的 70%」。**
- §6 配置项改名：「分成比例（万分比）」→ **「创作者分成比例」（万分比，对毛收入；定义见 §3.1）**。
- 已按 §3.1 的图（`show_widget`）向用户解释：账目口径链 收入 R ×30% → 激励池 P → 折算 → PIX 负债 L；真钱口径链 收入 R 全额 → 现金池 C → 提现出账；虚线表示 L 只在提现时从 C 扣。

## 账目修复：`carryInFen` 被二次打折（用户追问「30% 分给创作者？」时发现，已改）

用户继续追问「就是网站收入拿总的 30% 来分给创作者？」，复核公式链时发现**原公式是错的**：

```
❌ 原：P = floor((R + 上期结转) × rate / 10000)
✅ 改：P = floor(R × rate / 10000) + carryInFen      // 池余全额结转，不再乘比例
```

- **为什么是错**：`carryOut` 是**已经按比例切好、已经指定给创作者**的钱。下期再乘一次比例 = 把其中 `1−rate` 悄悄收归站里。数值反例：收入 1000、结转 20、rate 30% → 错算 `floor(1020×0.3)=306`（结转只"生效"6 元），对算 `300+20=320`。**消失的 14 元既没进 `poolFen`，也没记成站内收入 —— 无账可查**，§12 跨期守恒必然失败。
- 规则：**分成比例只作用于本期新增收入；池余全额结转、原样回流。**
- 连带澄清：§3.4 的「上期结转**现金**」是现金池 C 的定义项，与 `carryInFen` 不是同一个数字（原文措辞容易混，已加 ⚠️ 提示）。
- 改动落点：§3.1 计算链 + 两个池对照表 + 新增「为什么 carryIn 不再乘比例」反例表；§3.2 结转句；§0 资金闭环图；**§12 新增验收项「跨期守恒」**（断言 `poolFen === floor(收入×rate/10000) + carryIn` 而非 `floor((收入+carryIn)×rate/10000)`，专防此写法回归）。

**教训（可复用）**：涉及"按比例切 + 跨期结转"的资金模型，必须逐项问「每个加数是否都该再乘一次比例」；结转项几乎永远**不该**再乘 —— 它已经是上次乘完的产物。这类错误在单价上量不出来（差几毛钱），只在跨期账目对平（`Σpayouts + carryOut == pool`）时才暴露。

### 本轮新增的可复用规则

**① creators 板块排序口径（`sort` / `period`）—— 默认值即兼容红线**
`getTopCreators(limit, sort="followers", period="all")`：**默认值绝不能改**，存量配置只有 `count`，改默认会让不改后台的现网排序被动变化。
返回值的 `metric` 是**驱动本次排名的那个数**，四组合语义不同（followers+week = 窗口内**新增关注数**，不是累计粉丝数），所以展示必须走同一个 `creatorMetaText(resources, metric, sort, period)`（落在 `format.ts`），写死「粉丝」会把贡献分榜说成粉丝数。
后台两个编辑器（`home-admin/SectionEditor`、`site-admin/WidgetEditor`）都要加 `sort`+`period` 控件，**漏一个就会出现「配置能存但界面调不了」**。

**② TypeScript 联合类型的对象字面量赋值陷阱（真实踩到）**
给 `HomeSectionConfig` 的 creators 分支加 `sort` 后，`DefaultSectionSpec[]` 与 `buildConfig()` 双双报错：`Type '"followers"' is not assignable to type '"latest"|"popular"|"downloads"'` / `Type 'number' is not assignable to type 'never'`。
原因不是写错了，而是**联合类型里两个成员共用了 `sort` 这个名字**（list 的 `sort` 是 `latest|popular|downloads`），且 `stats` 成员是 `Record<string, never>`（能接任何对象，最容易成为报错对象）→ TS 的「最佳匹配」挑错成员。修法是给 creators 分支的 `sort` 一个**独有字面量集合**（本案例是补齐 `count + sort: "followers"|"points" + period` 后按分支精确匹配）。**下次往这类配置联合加字段，要预期这个报错并一次把 schema / 联合类型 / 默认值 / 两个编辑器四处同时补齐。**

## /browse 分类独立 title（防止同标题被重复收录）

用户原话：「给浏览也补充单独的title 切换分类的时候，防止搜索引擎收录同个标题」

诊断：`/browse` 的 `generateMetadata` 对所有非搜索态一律返回 `title: "浏览"`。而 `canonicalOf()` **只保留 `cat` 与 `page`** —— 也就是说 `/browse?cat=X` 这些 URL 是会被收录的，标题却全部相同 → 重复标题。（`type`/`sort`/`period`/`tag`/`q` 都不进 canonical，不构成重复，所以不动。）

改动（1 文件：`src/app/browse/page.tsx`）：

| 改动 | 说明 |
|---|---|
| 新增 `resolveCat(sp)` | 只有命中 `getCategories()` 里真实 slug 才算数；无效 slug 回落成「无分类」 |
| `canonicalOf(catSlug, sp)` | 签名从 `(sp)` 改为显式传已解析的 slug —— 无效 cat 不再进 canonical，收敛到 `/browse` |
| title 改为 | `cat ? "${cat.name} · 浏览" : "浏览"`，再按 `page > 1` 追加 `（第 N 页）` |
| `robots` | 搜索态（`q`）保持原样 `index:false, follow:true` |

**实测到的关键事实**（原以为要靠猜）：`/browse` 未改前渲染的实际 `<title>` 是 **`浏览 · 资源社区`** —— 根 layout 的 `title.template`（`%s · 站名`）**确实作用于子段页面**。所以分类标题写成 `${cat.name} · 浏览` 最终是 `游戏 · 浏览 · 资源社区`，**不能**再自己拼站名（会重复）。项目里首页 `app/page.tsx` 那句"模板不作用于与其同段的页面"只对**同段页面**成立，别推广到子段。
