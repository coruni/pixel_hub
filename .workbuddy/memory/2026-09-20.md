## 修复音视频（MUSIC / VIDEO）上传「无法正常使用」（对齐 ARTICLE / GAME）

用户报：「上传视频还是无法正常使用 请参考文章 或者 游戏类型 修复上传」（上一轮 9508ae1 只修了 accept 与进度条）。

- **根因 1（决定性）—— 服务端字段错误名与前端读取的 key 对不上，报错被静默吞掉**
  `avMetaSchema`（`src/lib/meta.ts`）校验失败时 `path: ["url"]`，即 `fieldErrors.url`；
  而 `av-section.tsx` 读的是 `fieldError(fieldErrors?.avUrl)` → 永远 undefined。
  结果：视频没传完就点提交 / 提交了空地址 → 服务端返回 `{fieldErrors:{url:[...]}}` → **页面毫无反馈**，看起来「点了没反应」。
  对照：GAME/ARTICLE 读的分别是 `downloads`、`mediaIds`，与 schema 一致，所以它们不犯这个错。

- **根因 2 —— AvSection 没有向宿主上报「上传在飞」，提交按钮不会锁**
  `AttachmentListEditor` 通过 `onBusyChange(inflight)` 让宿主禁用提交 + `onSubmit` 里 preventDefault 兜住回车；
  AvSection 没接这个契约（`UploadWizard` / `ResourceEditForm` 的 `attachBusy` 一直是 0）。
  于是「大视频还在传就点发布」必然走到根因 1 的静默失败。

- **根因 3 —— 上传成功回执被元数据抓取阻塞**
  `onFile` 原来 `setMsg(已上传…)` 排在 `await probeFile()` 之后；大视频读 loadedmetadata 最坏等 12s 超时，
  这期间 `uploading` 仍为 true，按钮一直停在「上传中…」，像卡死。

- **根因 4 —— `AttachmentUpload` 先清空 input.value 再用 FileList**
  `const fl = e.target.files; e.target.value = ""; onFiles(fl)`：Chrome 的 `input.files` 是挂在元素上的**同一份** FileList，
  先清空会把已捕获的引用一起清掉 → 消费方拿到空列表 → 点选文件「没反应」。改为先 `onFiles(fl)` 再清空。

- **改法**

  | `src/components/upload/av-section.tsx` | 新增 `onBusyChange?` prop（`uploading ? 1 : 0`）；`fieldErrors?.avUrl` → `?.url`；上传入口从行内按钮改为 `variant="dropzone"` + `useFileDrop`（`disabled: uploading`），与文章/游戏投放区同形；`onFile` 回执不再等 probe，probe 结果异步补进提示 |

## 续：上传视频「无法使用」的真实根因是**体积上限**，不是上面的契约问题

用户回「按照最合适的修改」。先按无浏览器流程实测复现（起 dev server + 铸管理员 cookie + 真发请求）：

| 请求 | 结果 |
|---|---|
| 946KB `.mp4` → `/attachment` | **200 OK**，落 `public/uploads/files/202609/*.mp4` |
| 300MB `.mp4` → `/attachment` | **413** `当前存储未启用 OneDrive，暂不支持超过 250MB 的文件` |

## 续：音视频走 OneDrive 但允许在线播放（`/od` 出口改成 Range 代理）

用户要求「音视频也属于附件所以也走 od，但是允许在线播放」——但当时 **Graph 凭据是空串、没有活跃盘**，真机走不通，
所以用「假 Graph」桩做端到端：`NODE_OPTIONS=--require prisma/_odstub.cjs` 起 `next start`，
桩把上游做成**故意不友好**（`content-type: application/octet-stream` + `content-disposition: attachment`），
断言只有路由自己裁定了响应头才能通过。

- 改动：`src/app/od/[driveId]/[...key]/route.ts` 从「一律 302 到 Graph 下载地址」改成**按扩展名分流**——
  音视频走 `fetchDriveContent` 代理转发（自定 `Content-Type`（`avMimeOf`）+ `Content-Disposition: inline` + `Accept-Ranges: bytes`，
  `Range`/`Content-Range`/`ETag` 透传，206 原样返回）；其余仍是 302 不占本站带宽。
  `av.ts` 加 `avKindByExt`/`avMimeOf`（mkv 这类不在系统 MIME 表里的必须显式给）。
- 验证（`prisma/_od.ts`，20 条断言全绿，跑完已删）：mp3 → 200 + `audio/mpeg` + `inline` + `Accept-Ranges`；
  mp4 `Range: bytes=1024-2047` → 206 + `Content-Range` 透传 + 只回 1024 字节；zip → 仍 302；
  非法 driveId → 400、不存在的盘 → 404。
- **坑（写断言时踩到）**：「路径穿越被拒」这条一开始 FAIL —— 客户端（fetch/undici）与 Next 路由都会在匹配前
  **把 `..` 规范化掉**，所以裸 socket 与 `%2e%2e` 都返回 200，但它们请求到的是被折叠后的**合法 key**。
  HTTP 层看到的 200 无法区分「被拒绝」和「已规范化」。正确做法：让桩把上游真正收到的路径写进日志文件
  （`%TEMP%/od-stub.log`），断言落在「交给上游的路径里没有 `..` 段」上。
  结论：路由 `safeSeg` 实际拦的是「编码斜杠」和「控制字符 %00」（400），`..` 由 Next 提前折叠。

## 续：构建告警 `Dynamic filesystem access`（`/api/dl`）

`src/app/api/dl/route.ts` 的本地文件分支原来用 `safeLocal(rest, root)`（内部 `path.resolve(root, rest)`）算绝对路径后
再 `stat()` / `createReadStream()`。打包器的**文件追踪只能静态分析 `path.join(process.cwd(), <字面量>, 动态尾段)`**，
路径一经函数计算就退化成「追踪整个项目」，于是 build 打出两条
`Warning: Dynamic filesystem access causes tracing of the whole project`（把 public 与全部源码都算进产物）。

- 改法：把**字面前缀留在真正调用 fs 的地方**——`const abs = path.join(process.cwd(), "public", target.sub, target.rel)`，
  并新增 `safeRel()` 只做段级归一化（拒 `..` / NUL / 空，`\` 统一成 `/`）。**越界改为结构上不可能**
  （结果一定拼在 `public/<sub>/` 之下），不再依赖「abs 前缀比较」兜。
- 重建后 `Dynamic filesystem access` 告警 **0 条**，编译成功。
- 教训：以后在本项目新增「按路径读写本地文件」的代码，写成 `path.join(process.cwd(), "…字面量…", 动态部分)`。

## 续：侧边栏「热门内容」列表溢出卡片

用户发截图：「修复侧边烂热门内容模块超出」——320px 侧栏里的排行列表，标题与点赞数（♡8）整行伸到卡片边框外。

- **根因：裸 `grid gap-1` 的隐式 auto 轨道**（`sidebar/widgets/feed.tsx` 四处列表都用这种写法）
  - `grid gap-1`（没写 `grid-cols-*`）= 一条 `auto` 隐式轨道。auto 轨道的**基数**取子项的
    **minimum contribution**，而 MiniRow 是 flex 容器、标题带 `truncate`（= `nowrap`）→ 行的 min-content ≈ 标题整行宽度
    → 轨道基数是 779px，容器内容盒只有 286px → 轨道直接顶穿卡片右边界。
  - **为什么之前加的 `min-w-0` 没修好**：`min-w-0` 加在**行内层**（`MiniRow` 里 `span.min-w-0.flex-1`）。
    min/max 对 min-content contribution 只是**夹取**（min-width 是下限，压不掉上限），所以行作为 flex 容器
    报给 grid 的 min-content 仍是标题整行宽。`overflow-hidden`/`min-width:0` 只有加在**grid item 本身**才能
    把它的自动最小尺寸清零 —— 最省事且绝对可靠的做法是容器侧写 `minmax(0,1fr)`（即 Tailwind `grid-cols-1`）。
- **改法**：`feed.tsx` 四处单列列表 `grid gap-1|gap-2` → `grid grid-cols-1 gap-1|gap-2`（`renderHot` 列表态 /
  `renderRandom` / `renderAuthorWorks` / `renderSameCategory`）。卡片态本来就是 `grid-cols-2`，没这问题。
